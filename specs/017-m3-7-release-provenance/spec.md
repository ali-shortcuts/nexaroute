# M3-7 — Secure release artifacts: SBOM, checksums, signatures, vulnerability gate

## Problem
The release pipeline built binaries and a SHA-256 manifest, but
shipped no SBOM, no signature, and no vulnerability gate bound to
the release revision: users could verify file integrity against a
manifest they had no reason to trust, and the standalone Security
workflow did not block a tag publish.

## Acceptance criteria
1. An SBOM (SPDX 2.3 JSON) generated by a pinned, checksum-verified
   Syft describes the shipped binaries and their embedded Go module
   inventory; its contents are validated against go.mod (names and
   versions) and it records repository/commit/version traceability.
2. SHA256SUMS covers every distributable asset including the SBOM,
   is generated only after all covered assets exist, never lists
   itself or the signature bundle, and is verified with
   `sha256sum -c`; missing/modified/unexpected assets are rejected.
3. The publish path signs SHA256SUMS with Sigstore keyless signing
   (GitHub Actions OIDC); `id-token: write` is granted only to the
   publish job; the signature is verified in-workflow against the
   pinned release-workflow identity and issuer before publishing;
   the bundle ships with the release.
4. govulncheck (same pinned action as the Security workflow) gates
   the exact release revision inside the release workflow's verify
   job; publish depends on it.
5. The workflow_dispatch dry run stays non-publishing and exercises
   build, SBOM, checksums, the artifact round-trip, and a clearly
   separated ephemeral-key signing mechanics test (never the release
   identity, never uploaded).
6. Users get copy-pasteable verification instructions
   (docs/RELEASE_VERIFICATION.md).

## Honest boundary
The keyless signing path can only be exercised end to end by a real
tag publish, which this task must not perform. Until the first real
release runs it, the signature requirement is implemented and
mechanics-tested but its real-world verification stays UNVERIFIED.
