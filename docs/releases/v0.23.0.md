# NexaRoute v0.23.0

NexaRoute v0.23.0 builds on v0.22.0 with stronger routing transparency, cost operations, provider acceptance tooling, protocol-conformance evidence, and repeatable load qualification. This release focuses on making runtime decisions and operational claims easier to inspect and verify; it does not claim that every upstream provider feature has been validated against a commercial tenant.

## Highlights

- **Routing explainability and preview.** The router can explain the same candidate-eligibility funnel used for real requests. The authenticated route-preview endpoint reports selected candidates, exclusions, and stable redacted reasons without making upstream calls or exposing session/selection keys.
- **Budget threshold alerts.** Virtual-key spend can trigger asynchronous webhook notifications at configured thresholds. Delivery is bounded and uses the egress/SSRF policy; durable stores can deduplicate fired thresholds across restarts.
- **Live request activity.** The admin Activity view exposes bounded request lifecycles, per-attempt outcomes, latency/TTFT, usage and cost basis, filters, and request deep links using backend events rather than fabricated UI telemetry.
- **Decision-policy observability.** Decisions can carry a reproducible policy version; replay reports version mismatches, and opt-in shadow evaluation observes alternative choices without changing served traffic or adding inference calls.
- **Provider onboarding acceptance.** The provider-accept command exercises bounded model discovery and generation probes, including custom/manual models and model provenance. Preset catalog and category-filter defects found during acceptance were corrected.
- **Protocol conformance and drift evidence.** The versioned conformance registry and the opt-in live-canary command separate fixture-backed behavior from genuinely observed upstream capabilities. Unsupported dimensions are not promoted to LIVE-VERIFIED without evidence.
- **Provider media addressing.** Azure OpenAI media routes use deployment-specific paths and API-version parameters where supported; unsupported provider/media combinations are rejected instead of being silently rewritten into invalid calls.
- **Performance and resilience qualification.** Reproducible benchmark/load profiles, measured baseline/SLO documentation, stress/soak stages, resource sampling, and failure-injection evidence make local performance checks repeatable. The race-stage duration leak and the `0s` soak-duration handling were fixed.

## Fixes and reliability

- Wired the preset-category filter to its existing view state and added an invariant test that detects rendered UI actions without handlers.
- Made first-run browser assertions deterministic when the provider preset catalog is still loading.
- Treated zero-valued Go soak durations such as `0s` as the documented “disabled sustained phase” sentinel while retaining fail-fast behavior for malformed or negative durations.
- Pinned the race-soak stage to a bounded duration so a longer operator-requested soak cannot make that stage exceed its own test timeout.

## Verification and evidence boundaries

The tagged release is published only after the release workflow succeeds on that exact tag. The workflow runs the full repository verification, reachable Go vulnerability gate, stress and runtime smoke tests, release builds for Linux amd64/arm64, SBOM generation and validation, exact SHA-256 manifest coverage, installer lifecycle tests, embedded-version checks, and keyless Sigstore signing of the published checksum manifest.

CI and conformance tests use protocol-faithful local fixtures where noted. The provider-acceptance and conformance-canary evidence recorded for this release used a controlled loopback upstream, not commercial provider tenants. Real-provider behavior is therefore not claimed as verified by those runs. Live external OIDC-provider, Vault/keyring, Kubernetes-cluster, and real ComfyUI inference interoperability remain environment-dependent and must be verified in the target deployment; see [External verification](../EXTERNAL_VERIFICATION.md) and [Known gaps](../KNOWN_GAPS.md).

## Upgrade and compatibility

No additional breaking configuration change is introduced specifically by this release. Preserve a backup of configuration and state before an upgrade, and follow [Installation](../INSTALLATION.md) and [Release verification](../RELEASE_VERIFICATION.md). Plain HTTP provider URLs remain restricted to explicitly spelled loopback hosts; use HTTPS for remote upstreams.
