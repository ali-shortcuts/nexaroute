# Unreleased

## Features

- Code scanning: the remaining open CodeQL alerts on main are resolved — the provider adapter no longer sizes a map from a config-derived length (uncontrolled allocation), and the two findings that are false positives by design carry in-code `codeql[...]` suppressions with recorded justifications (request forgery: destinations come only from operator configuration and the egress policy pins dialable hosts at connect time; weak hashing: the credential-scope value is a truncated change-detection fingerprint, not a password verifier). Dispositions are indexed in docs/SECURITY.md.
- Budgets & Cost page (M2-3): the admin UI gains a Cost page over the live usage snapshot — total estimated cost and tokens, per-deployment cost with share bars, per-identity token totals, and exports (identity CSV via the existing endpoint, per-deployment CSV and cost JSON generated client-side). Budget limits configured on keys are listed when the budget backend provides them; webhook budget alerts are a separate follow-up, implemented by neither the budget backend (PR #329) nor this page (PR #338).
- Cost page budget visibility fix (E4 review): `GET /admin/api/client-keys` now preserves `budget_usd` (the field PR #329 added to the config model was dropped by the client-key response), emitted for every key — 0 means no cap — so the Cost page can actually list configured budgets; no secret or key-hash material is exposed. The Budgets panel now distinguishes its states honestly — configured budgets, none configured, budget data not exposed by the backend, key records not visible to the caller's role, and key records unavailable — instead of presenting every empty state as "backend pending", and the per-identity table discloses its 100-row cap ("Showing the first 100 of N identities"). This PR is stacked on PR #329 (base retargeted accordingly).
- Versioned price book, record-time costing and virtual-key budgets (M5-6): new pricing.versions[] price book (effective-dated per-deployment rates incl. optional cache read/write rates) governs cost-aware routing prices and spend accounting; usage is now priced WHEN RECORDED under the active version and attributed per version (cost_by_version_usd), so price edits do not reprice usage that has a recorded cost (records without one are estimated from model-config prices, and those estimates can change when the fallback rates change). Cache read/write tokens join token accounting on the canonical and Anthropic-native paths with per-dialect billing conventions (no double-charging of cached input). Virtual keys gain budget_usd: atomic admission reserves settled to actual cost on the first usage report, 402 on exhaustion, cache hits release the hold, unsettled reservations commit at estimate after 15 minutes; budget state resets on restart (documented).
- Added no-eligible-deployment warnings (M3-3): static, configuration-only eligibility warnings (empty referenced pools, route profiles with no usable deployments across their fallback chain, unsatisfiable `no_training` profiles/virtual keys, no enabled deployments) are computed during config load, printed at startup, and exposed via the admin snapshot and settings save responses — advisory only, never a validation failure. The admin snapshot also gains a per-profile `route_eligibility` view with candidate counts and current health-based exclusion reasons (privacy-filtered, provider unavailable, retired, cooldown, health not yet established).
- Added `nexaroute privacy audit` (M3-2): a read-only CLI that inspects configuration and runtime privacy policy surfaces locally — plaintext credentials at rest, credential-bearing or cleartext provider URLs, unsatisfiable `no_training` requirements for route profiles and virtual keys, egress deny-policy, cache and access-log settings — with deterministic exit codes (0/1/2) and text or JSON output. It never prints secret values and never modifies the config file.
- Admin-configurable egress allow/deny policy: a new top-level `egress` config section (`deny_hosts`, `deny_cidrs`, `allow_hosts`, `allow_cidrs`) lets operators restrict which hosts and networks providers may connect to, beyond the built-in special-purpose IP blocklist. Deny lists take precedence and are enforced at URL validation and again for every DNS-resolved address at dial time (PR #283). See `docs/CONFIGURATION.md` ("Global egress policy").

## Security

- Release provenance (M3-7): releases now ship a Syft-generated SPDX SBOM covering the shipped binaries and their embedded Go module inventory, the SHA256SUMS manifest covers the SBOM as well, the manifest is signed with Sigstore keyless signing (GitHub Actions OIDC, verified against the pinned release-workflow identity before publication), and a govulncheck gate runs on the exact release revision in the release workflow. See docs/RELEASE_VERIFICATION.md. The keyless signing path is exercised end-to-end only by a real tag publish; `workflow_dispatch` dry runs test signing mechanics with an ephemeral in-job key that is never the release identity.
- Client keys are hashed at rest and TPM quotas settle to actual usage (M3-8): legacy `client_auth.keys` plaintext is migrated automatically to SHA-256 digests (`client_auth.key_hashes`) on load and before every save — existing keys keep working, no usable client credential remains in the config file. A global `client_auth.tpm` ceiling now binds legacy clients as well as virtual keys, and TPM admission reservations are reconciled with provider-reported usage after each request (over-estimates refunded, under-estimates charged).
- The admin security store is now behind a runtime-selectable backend interface (M4-1): `admin.security_store_backend` (`bbolt` default) with a shared backend contract suite; the Redis/PostgreSQL adapters land with M4-2, and selecting one today fails closed at startup rather than silently substituting a different store.
- External-integration hardening and verification (M4-7, local scope): the OIDC verifier now resolves signing keys from the issuer's CURRENT JWKS document on every login callback — previously the cached key set honored a retired IdP signing key for the life of the process; a new rotation test covers rollover and retired-key rejection. The linux keyring provider gains hermetic `secret-tool` stub tests pinning its fail-closed headless contract. A reference Vault KV v2 command helper (`scripts/key-provider-vault-kv.sh`) ships with fake-Vault wire tests, and SECURITY.md now states the Vault Transit boundary exactly: Transit envelope mode is not implemented; the provider contract loads raw key material. `docs/EXTERNAL_VERIFICATION.md` is the operator runbook for closing the remaining live boundaries (real IdP, real Vault, real keyring daemon), which stay UNVERIFIED.
- Redis security store (M4-2b): `admin.security_store_backend: "redis"` stores admin sessions and the audit hash chain in Redis (hashes under `nexaroute:security:*`). Mutations plan with the same chain logic as the other backends and commit through a version-checked Lua script (optimistic CAS with bounded retries); session touches use a field-level compare-and-set. It passes the same backend contract suite and audit-hash parity checks as bbolt/PostgreSQL against a real Redis in CI. Durability follows the operator's Redis persistence (AOF/RDB) and replication configuration, as with the Redis control-plane backend.
- PostgreSQL security store (M4-2a): `admin.security_store_backend: "postgres"` now stores admin sessions and the audit hash chain in PostgreSQL (tables `nexaroute_security_*`), so multiple gateway processes can share them. The adapter passes the same behavioral contract suite as the local bbolt store, produces byte-identical audit chain hashes for identical operation sequences (verified in CI against a real PostgreSQL), serializes writers across processes on the chain allocator row, and verifies the full chain inside every append transaction. `security_store_url` additionally accepts `env:VARIABLE_NAME` so credentials stay out of durable config. The Redis security-store adapter follows in the next PR; selecting it still fails closed.
- Bug fix: the documented `nexaroute config validate|diff|dry-run` subcommand was unreachable — the binary ignored it and started the gateway. All subcommands now route through a single tested dispatch function (with a regression test that fails if any subcommand loses its routing).
- New operations CLI commands (M4-3): `nexaroute doctor` runs read-only installation diagnostics (config, permissions, master-key resolvability, audit-chain verification, control-plane readiness — statuses and counts only, exit 0/1/2); `nexaroute backup` writes a single hash-verified bundle (config, a consistent online snapshot of the audit/security store, file-backend control-plane state; the master key is fingerprint-recorded but excluded unless `--include-master-key` is given); `nexaroute restore` verifies the entire bundle before writing anything and installs atomically, refusing to overwrite differing files without `--force`.
- Backup/restore hardening (M4-3 review): a backup now fails on any unreadable source instead of silently omitting it (only genuinely absent files are skipped), refuses an `--out` path that aliases a source file (including symlink/hard-link aliases), and bounds bundle parsing (2 GiB per entry, 4 GiB aggregate, enforced from tar headers before bodies are read). Restore journals pre-install bytes and rolls back already-installed files when a later install step fails (best-effort — see OPERATIONS.md for the exact guarantee limits), and its config-validation fallback is restricted to a positively identified missing master key: semantically invalid bundled configs are rejected before anything is written.
- Backup/restore hardening, second review round (M4-3): restore now also refuses aliased install destinations and payloads inconsistent with the bundled configuration's backends before writing; the rollback journal preserves pre-restore modes and symlink targets and is itself preserved (path reported) when a rollback is incomplete; `nexaroute doctor` reports inaccessible security-store/control-plane paths as failures instead of "not created yet" (and no longer risks a nil FileInfo panic when the config Stat fails); and backup creation enforces the same entry/aggregate limits while staging, with source reads bounded before allocation, so a produced bundle can never be one restore would reject for size.
- Backup/restore hardening, third review round (M4-3): destination canonicalization is now a component-wise resolver — a symlinked ancestor with not-yet-existing deeper directories previously canonicalized aliased destinations to *different* strings, so a colliding restore was silently installed (proven by a failing-then-passing regression test). The restore journal is now a durable, versioned transaction record (`nexaroute-restore-journal/1`, fsynced manifest with destinations, modes, symlink targets, progress and state), so a killed or crashed restore can be rolled back afterwards with the new `nexaroute restore --recover <journal-dir>` (completed journals are cleaned up, never replayed; unknown formats are refused); interrupted journals are reported by both `restore` and `doctor`. OPERATIONS.md states the exact recovery contract and the residual TOCTOU assumption (destination directories must not be writable by untrusted users).
- Backup/restore hardening, fourth review round (M4-3): journal durability and recovery validation completed. Saved pre-restore copies are now fsynced individually through checked open-handle writes (previously only the journal directory was synced), the journal directory entry and its parent are synced on creation and deletion, and any journal-preparation failure aborts before a destination is touched. A completion that cannot be persisted is no longer silently ignored: restore exits nonzero and preserves the journal (still `installing`) rather than reporting success while deleting the only recovery record. `restore --recover` now strictly validates the journal as untrusted input before mutating anything — directory/manifest type, privacy and ownership, known states, well-formed IDs, an allowlist of entry names, absolute non-aliased destinations, consistent pre-state metadata, exact saved-copy names, and a verified SHA-256 per saved copy — with adversarial tests for traversal names, symlinked or tampered copies, aliases, contradictory metadata and untrusted directories; every rejection leaves destinations untouched and the journal preserved.
- Backup/restore hardening, fifth review round (M4-3): destination directory synchronization. Installs previously renamed files into place without ever syncing the destination directory, so a "successful" restore was not durable at the directory level. Every destination mutation — install, in-process rollback, and `--recover` recovery — is now followed by a sync of the destination's parent directory (and grandparent, covering parents the install itself created) before the transaction may advance, complete, or discard the journal. Failure semantics are explicit and tested with injected sync failures: a landed rename counts as installed even when its sync fails (it joins the rollback scope), and a rollback/recovery mutation whose sync fails counts as unconfirmed — destination named, journal preserved, operation retryable because rollback and recovery are idempotent. No real power-loss testing is claimed; guarantees remain bounded by filesystem and hardware fsync behavior, as documented in OPERATIONS.md.
- Deployment assets (M4-4): a Helm chart (`deploy/helm/nexaroute`) with hardened non-root security contexts, health/readiness probes, PVC-backed state and secret-referenced database wiring; a hardened system systemd unit (`deploy/systemd/nexaroute-system.service`) alongside the existing user unit; a CI `container` job that builds the distroless image for amd64+arm64, smoke-runs it, and lints/renders the chart with posture assertions; and a new DEPLOYMENT.md guide. A live Kubernetes cluster install remains unverified.
- The control-plane PostgreSQL backend is now wired end to end (M4-1): `control_plane.backend=postgres` uses the pgx driver with the DSN taken only from the configured environment variable, a bounded pool, a startup readiness ping, and checksum-verified migrations; startup fails closed (secret-safe errors) and never falls back. A per-namespace advisory lock also fixes a race where two competing first writes to a fresh control-plane namespace could leak a raw database unique-violation instead of a deterministic revision conflict.
- The control-plane Redis backend is wired too (M4-1): `control_plane.backend=redis` uses a go-redis client (URL only from the configured environment variable, bounded pool/timeouts/retries, startup ping, fail-closed secret-safe errors) and stores snapshots as per-namespace hashes guarded by atomic Lua compare-and-set scripts with the same revision semantics as the file/PostgreSQL stores. Redis durability depends on the operator's Redis persistence/failover configuration (see CONFIGURATION.md).

- Provider egress now blocks the full IANA special-purpose space, including carrier-grade NAT (`100.64.0.0/10`, which contains the Alibaba metadata address `100.100.100.200`), TEST-NETs, benchmarking, reserved, Teredo, site-local and `::/96`. NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) addresses are judged by the IPv4 address they embed, so legitimate IPv6-only deployments keep working.
- Loopback is reachable only when the provider host is spelled as loopback (`127.0.0.1`, `::1`, `localhost`). A public DNS name that resolves to loopback is rejected at dial time.

## Breaking

- Plain `http://` provider base URLs are now accepted only for explicit loopback hosts. Previously the loopback opt-in was derived from the URL scheme, so `http://<any host>` was accepted and API keys could be sent without TLS. Use `https://`, or a loopback address for local development (for example Chat2API on `http://127.0.0.1:5000/v1`).
