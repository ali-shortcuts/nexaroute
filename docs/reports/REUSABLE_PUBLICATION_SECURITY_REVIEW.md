## 3. Propagation rules and narrow-controller design

GitHub's [reuse reference](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations) says the called workflow's `github` context and `github.token` are associated with the caller; nested `GITHUB_TOKEN` permissions can be maintained or reduced, not elevated beyond the caller. If a calling job does not specify permissions, default permissions apply. A caller that already has Contents write may pass that authority to the callee; a token from another repository normally has its caller-repository scope, not automatic NexaRoute write. Separate PATs, App tokens, cloud credentials or inherited secrets have their own permissions and are **not** constrained by the `GITHUB_TOKEN` ceiling.

[GitHub's reusable-workflow guide](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) states named secrets are passed one hop at a time; `secrets: inherit` can pass all caller-accessible secrets across eligible same-organization/enterprise boundaries and can expose names not declared in the callee. Environment secrets require a job declaring the environment; the call job cannot itself declare an environment. A callee job's environment and same-name-secret precedence must be reviewed in its actual caller-repository context. Inputs and artifacts remain untrusted even if typed. Same-repository `./` or `$/` uses the caller's commit; `owner/repo/.github/workflows/file.yml@<full SHA>` pins the callee to an immutable commit. A full SHA does not itself authorize the caller or candidate.

**Proposed only; neither controller nor privileged reusable workflow is implemented:**

1. A single reviewed controller on protected `main` (or a separately protected automation repository with a separately verified identity boundary) is manually started only by specifically authorized operators. At run time it checks caller repository ID and owner ID, caller workflow identity, event, protected `refs/heads/main`, exact approved current candidate SHA, and independent authorization. It fails if main or approval changes before publication. Untrusted PR code, arbitrary ref selection, caller-supplied credentials and unverified artifacts cannot determine publication.
2. Its only privileged job calls a separately reviewed reusable publication workflow at an explicit **full immutable commit SHA**, never a mutable tag/branch or local relative path. The required SHA, trusted caller identity and candidate are independently verified, not accepted solely as caller inputs. The callee re-runs completion-only checks for #646–#654, current main equality, independent acceptance/content review and the exact candidate immediately before use. GitHub REST observations remain non-atomic; prevent/resolve concurrent changes with a documented owner-controlled approval protocol and revalidation.
3. Top-level/default permissions are none or read; the calling job grants only the required `contents: write`/`id-token: write` ceiling, and callee verification jobs explicitly reduce permissions. Only the reviewed publish job obtains publication authority and declares `release-publication`; its secret/identity is scoped to that job after environment approval. Do **not** use `secrets: inherit` or accept caller-provided publication credentials. Do not execute code from the candidate, untrusted artifacts, cache, or arbitrary actions in a credential-bearing job. The publisher independently verifies artifact digest/provenance and binding to the exact reviewed candidate, then performs only the approved operation. A separate automation repository requires a narrowly installed GitHub App for target-repository publication, not an assumption that its `GITHUB_TOKEN` targets NexaRoute.
4. Audit all alternative write-capable workflows and credentials, direct API clients and admin bypasses. An allowed caller/callee identity alone is not proof that inputs, artifacts, a publication credential, or candidate code are trustworthy. The design stays unimplemented until the owner authorizes it and independent reviewers approve its threat model and negative tests.

## 4. OIDC, historical `security.yml`, and provider reality

Confirmed GitHub-side observation: OIDC customization read returned `use_default: true`, `use_immutable_subject: true`, with subject prefix `repo:ali-shortcuts@191999077/nexaroute@1380855867`. This is not an assertion about any cloud provider. Current release's keyless signing uses Sigstore; the runner-local Keycloak/Vault acceptance harnesses are not evidence of a deployed cloud IAM trust. The actual cloud providers, accounts, roles, trust conditions and audiences are **unknown** and inaccessible here.

For jobs in a reusable workflow, GitHub's [OIDC reusable-workflow reference](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows) documents `job_workflow_ref` as the called workflow path/ref; ordinary `repository`, `ref` and other run claims describe the caller. GitHub also documents `job_workflow_sha` for the called reusable workflow. A future trust should require the real issuer, exact expected provider audience, immutable caller repository/owner IDs, approved caller ref/environment, and exact reviewed called workflow identity and SHA where the provider can enforce them. `job_workflow_ref` is not generally present for ordinary non-reusable jobs. Environment-based default subject typically does **not** encode the branch ref: require ref independently, or a verified custom subject/other control rather than assuming it is included.

GitHub documents direct custom-claim support for Google Cloud and HashiCorp Vault, while its AWS guidance says AWS does not support custom GitHub claims. For a provider that supports only `sub`/`aud`, GitHub documents subject customization such as `include_claim_keys: ["repo", "context", "job_workflow_ref"]`. The owner must first inspect actual issued claims, include any additionally required `ref`/identity keys only where supported, establish the precise provider-specific subject format and equality conditions, then configure matching cloud trust **before** changing GitHub's subject template to avoid outages. Do not assume this example template alone enforces both environment and ref, or invent an AWS, Azure, Google, Vault or other provider role condition for an unidentified provider. Provider IAM administrator must supply sanitized evidence of the actual condition syntax, active policy and successful/denied exchanges; no such evidence is available.

Historical `security.yml` requested `id-token: write` in at least one scanned history blob while current `security.yml` is ordinary CI. If a real cloud trust accepts a broad repo subject, historical jobs might be able to obtain the role; issuance alone is not proof the role exists or trusts it. Narrow the real provider's role trust to the approved repository, ref/environment and reviewed reusable identity/SHA, and remove obsolete broad bindings; where the provider cannot enforce the conjunction, remove that trust or introduce a separately reviewed broker. Such a change can preserve legitimate CI if CI does not depend on the removed trust, but current dependencies are **unknown**. Verify this with the provider administrator and controlled tests; do not assume narrowing is non-disruptive. Scope Sigstore certificate identity verification separately from cloud role access.
