## What this control can and cannot do

GitHub's [workflow execution protection documentation](https://docs.github.com/en/actions/how-tos/administer/control-workflow-execution) describes centrally enforced actor and event allowlists and workflow-path targeting. Disallowed runs are rejected before workflow execution, including workflow files at historical refs if the effective policy matches that run and path. GitHub describes the behavior in its [Actions policies concepts](https://docs.github.com/en/actions/concepts/about-actions-policies). This is materially different from editing the current `release.yml`: a tag pointing at an old commit uses the old file. GitHub's evaluate mode is Enterprise Cloud only; do not assume it exists for this personal account. GitHub documents exemptions for some GitHub feature processes from actor restrictions; the owner must investigate any applicable exemptions and test effective behavior.

A policy matching only `.github/workflows/release.yml` can deny `push` for that path without automatically denying ordinary CI paths. A separately scoped actor restriction can allow only specifically approved users or apps to dispatch that path. This is **not** ref filtering: an allowed dispatcher might choose an old or otherwise untrusted ref. Nor does that path restriction cover publishers at other workflow paths, an allowed actor misusing credentials, or a release created directly through the API/UI outside Actions. Path selection and overlapping/inherited policies must be inspected and tested, not assumed. In particular, any proposed release controller needs its own independently enforced trusted-ref and candidate validation; no such controller is implemented or certified here.

The default `GITHUB_TOKEN` setting is a default, not a universal ceiling: GitHub says a workflow's `permissions` can modify it. Historical release files explicitly request `contents: write`; several request `id-token: write`. A read-only default or a protected environment on a different workflow is not enough. See [workflow permissions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository) and [token permissions](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/controlling-permissions-for-github_token). An environment's secrets/review requirements apply only to jobs declaring that environment; they do not remove a historical job's `GITHUB_TOKEN`. OIDC issuance also does not itself imply any cloud role trusts the token.

### Lockfile is a separate supply-chain control

Current checkout has no `.github/workflows/actions.lock`; lockfile protection is **not** known to be configured. [GitHub's lockfile docs](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles) cover step-level `jobs.<id>.steps[*].uses` and transitive action dependencies, but do **not** pin job-level reusable workflow references (`jobs.<id>.uses`); pin those by full SHA and review the called repository and its own lockfile. [Require lockfile](https://docs.github.com/en/actions/how-tos/administer/control-workflow-execution#require-lockfile) blocks targeted workflows not onboarded, even those with no `uses`; if a called reusable workflow is not onboarded in its own repository, it blocks the caller. It does not constrain arbitrary `run:` commands, checked-out local code, credentials, actor/event, or ref. Inspect local-path action limitations and generated diffs; generate/review/verify lockfiles before any active rollout. Evaluate mode is Enterprise Cloud only; without it, pilot in an authorized isolated repo before targeting onboarded paths. Historical refs may lack lockfiles and be blocked when targeted, but do not treat that incidental effect as the primary publisher boundary or as verified behavior.
