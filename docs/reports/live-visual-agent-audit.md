## 1. Current NexaRoute State

NexaRoute is a Go gateway/control plane with an embedded static frontend. The production executable embeds `internal/httpapi/web/*` through `//go:embed` and serves it from the same HTTP server. The current frontend is a compact single-file application in `internal/httpapi/web/app.js`, with `index.html` and `styles.css` alongside it.

The v0.14 control plane currently has the five required top-level surfaces: Overview, Providers, Routing, Activity, and Settings. The backend already exposes authoritative snapshot, provider, settings, simple-route, provider discovery/check/test, and event-stream APIs. Provider credentials are write-only in the admin responses.

The existing Overview contains a static topology and a separate decorative hero orbit. The topology currently renders Client → NexaRoute → a bounded list of configured deployments from snapshot state. It does not yet render a request-correlated execution journey.

## 2. Existing Reusable Components

- `internal/httpapi/web/app.js`: centralized frontend state, API helper, rendering, provider/routing/settings workflows, Activity filtering, and the sole current SSE reader.
- `internal/httpapi/web/index.html`: embedded shell, five-item navigation, skip link, live status, notice region, and dialog root.
- `internal/httpapi/web/styles.css`: existing v0.14 tokens, responsive layout, semantic status colors, and `prefers-reduced-motion` CSS handling.
- `internal/events/bus.go`: bounded ring buffer, monotonic sequence, bounded subscriber count/channel, snapshot/since APIs, and field truncation.
- `internal/httpapi/admin_events.go`: authenticated SSE with bounded historical preload, `since`, `Last-Event-ID`, keepalives, and one bus subscription per connection.
- `internal/httpapi/admin.go`: authoritative snapshot serialization and safe admin/provider surfaces.
- `internal/httpapi/openai.go`, `anthropic.go`, and `canonical_path.go`: real request lifecycle event emitters and terminal route events.
- Existing Activity event table and Overview topology are the correct surfaces to evolve; a second dashboard or decorative panel is not appropriate.
- Existing Go tests cover event bus bounds, SSE resume, routing/failover, protocol paths, secret safety, and browser control-plane flow.

## 3. Current Event Model

The wire event is `events.Event` in `internal/events/bus.go`. It includes `seq`, `time`, optional `request_id`, `kind`, optional deployment, message, latency, status/error fields, and bounded routing/task/decision metadata. It does **not** currently contain an `epoch` field despite some documentation describing `(epoch, seq)` ordering.

The bus assigns a process-local monotonic `seq`, stores a bounded ring, and delivers to bounded non-blocking subscriber channels. Slow subscribers do not backpressure routing. SSE sends historical events first, then live events, and uses the event sequence as SSE `id`.

The request path emits real request-correlated events including `route_fail`, `failover`, `route_ok`, `candidate_exhausted`, `route_timeout`, `client_disconnect`, `stream_fail`, `response_decode_fail`, `stream_fail_precommit`, `model_retired`, `model_unavailable`, cache/compatibility diagnostics, and production lifecycle events. The production lifecycle vocabulary is eight kinds: `model_healthy`, `model_failed`, `model_recovered`, `model_cooldown`, `provider_rate_limited`, `route_changed`, `request_failover`, and `recovery_failed`.

Important limitation: there is no consistently emitted request-correlated `route_attempt` event. The request code explicitly documents that noisy per-request attempt logging was removed. A successful terminal event exists as `route_ok`; failures and failover events exist. The next actual attempt is not explicitly identified by a frontend-safe start event; it can only be inferred from the next request-correlated terminal/failure event or supplied by a minimal backend observability delta.

## 4. Current Topology Implementation

The Overview topology is generated by `overviewView()` and `topologyTargets()` in `internal/httpapi/web/app.js`. It displays Client, NexaRoute, and up to three configured deployments from the snapshot, with health dots sourced from snapshot health. It is configuration/health topology, not execution topology: it does not have a request ID, active execution object, path state, attempt state, terminal state, selection, pinning, or accessible execution narration.

The existing route cards also show backend-derived public model, route behavior, and target membership. Candidate pools, profiles, fallback chains, and virtual endpoints are kept behind Advanced in Routing, which matches the v0.14 information architecture.

## 5. New Concept Mapping

| Live Visual Agent concept | Current authoritative source | Safe initial mapping |
|---|---|---|
| Client | Request existence and request ID from event | Show only once a real request-correlated event is received |
| Gateway / NexaRoute | Existing Overview topology and route path | Static gateway node; active state is driven by tracked execution |
| Public route | `VirtualEndpoint`, `PublicModel`, or event fields when present | Display only when event/snapshot correlation supplies it |
| Eligible/attempted target | Snapshot deployment membership plus request event deployment | Do not call configured targets attempted without event evidence |
| Provider/model | Snapshot deployment/provider metadata and event deployment ID | Correlate deployment ID to snapshot; omit if unavailable |
| Failure | Request-correlated `route_fail`, `stream_fail`, timeout, or terminal error event | Semantic failure only for supported event kinds |
| Failover | Request-correlated `failover` / `request_failover` followed by another real event | Never calculate fallback order in browser |
| Success | Request-correlated `route_ok` | Terminal success with backend latency |
| Idle | No active tracked request | Static “Waiting for requests”; no traffic animation |

## 6. Directly Reusable Pieces

The first implementation can reuse the existing embedded delivery, state ownership, admin API helper, event bus, SSE endpoint, snapshot model, deployment/provider lookup, Activity filtering, page lifecycle, and design tokens. The existing `pagehide` abort is a useful starting point but is insufficient for a dedicated renderer lifecycle.

The frontend can remain dependency-free JavaScript. The topology can be extended using DOM/CSS and a small presentation-only SVG or CSS path layer after auditing accessibility and DOM cost. No graphics library or new frontend framework is justified by the current stack or expected concurrency.

## 7. Missing Pieces

- A single frontend event normalization and execution-tracking layer shared by Activity and Overview.
- Request-keyed bounded execution state with duplicate/stale/reordered event handling.
- A documented mapping from actual backend event kinds to visual semantics.
- An authoritative way to distinguish attempt start from attempt failure/success when the current events do not provide it.
- Active execution topology state separate from static configured topology.
- A visual agent renderer with explicit start/stop/cleanup and reduced-motion/off modes.
- Request selection/pinning and “View in topology” integration.
- Accessible live narration of request progress.
- Gap/restart handling consistent with actual server behavior; current wire data has `seq` but no `epoch`.
- Performance instrumentation and browser evidence for idle, single request, burst, long run, and background tab behavior.
- Deterministic real browser acceptance against a local mock upstream, including failure/failover.

## 8. Conflicts

1. The brief requires `(epoch, seq)` handling, but `events.Event` and SSE currently expose only `seq`; existing docs/specs are ahead of implementation. This must not be silently papered over in the browser.
2. The brief requires one real path transition per actual attempt, but per-attempt start is not currently emitted consistently. A renderer cannot truthfully animate “attempting Provider A” from `route_ok`/`route_fail` alone without either a safe backend addition or a narrower semantic.
3. The frontend currently opens SSE with `?limit=50` and does not send `since` or `Last-Event-ID`, does not deduplicate sequence numbers, and does not detect gaps. This conflicts with the documented reconnect contract.
4. `refresh()` calls `startSSE()` after every refresh; `startSSE()` aborts the prior controller, but there is no bounded reconnect loop or cursor continuity. This is one owner, but not yet a robust event transport.
5. Activity currently renders raw event messages and request IDs but has no shared request journey model, request selection, or accessible live status.
6. Existing Overview hero orbit is decorative ambient animation-like design language; the new requirement explicitly prohibits confusing decorative motion with real traffic. It should be reduced or removed as part of the Overview evolution.

## 9. Backend Delta, If Any

**Initial recommendation: zero backend delta for Phase 3 correlation proof.** The existing request events are sufficient to prove request ID correlation, real failure, failover signal, and terminal success/failure in a static execution surface.

A minimal backend delta becomes justified only if the first real vertical slice cannot truthfully show attempt progression. Candidate additive metadata should be privacy-safe and useful to observability beyond animation: an explicit request-correlated attempt-start event containing deployment identity and bounded public-route metadata, and/or a process `epoch` included consistently in event/snapshot/SSE contracts. Any such change needs Go tests, event-contract documentation, and security review.

Do not add backend events solely to make gait prettier. Do not add raw prompts, responses, credentials, client keys, or authorization headers.

## 10. Frontend Delta

The frontend should be split into small static modules only if the current Go embed can serve them without a build step or production server. A compatible low-risk shape is:

- `event-stream.js`: one authoritative fetch/SSE owner with cursor/gap/reconnect policy.
- `execution-tracker.js`: normalization, request-keyed bounded state machine, and subscription API.
- `live-topology.js`: topology model and selection/pinning controller.
- `visual-agent.js`: presentation-only renderer, motion modes, RAF cleanup.
- `app.js`: shell, API mutations, page rendering, and orchestration.

Before splitting, preserve the current embed contract and prove module loading works under the embedded Go file server. If module loading complicates the embedded delivery, keep a carefully bounded `app.js` with explicit internal boundaries rather than introducing a bundler.

## 11. Recommended Architecture

```text
Go routing/backend
        ↓
privacy-safe events + authoritative snapshot
        ↓
EventStreamClient (one owner)
        ↓
EventNormalizer (one tested mapping)
        ↓
ExecutionTracker (bounded request-keyed state)
        ├── Activity
        └── LiveTopology / VisualAgent
                ↓
        presentation-only renderer
```

The renderer receives immutable execution snapshots and never calls routing APIs, chooses targets, computes fallback, or invents health. Selection and pinning only alter the displayed request. The tracker must tolerate unknown/malformed events safely and must not animate historical preload as new traffic.

Use a small bounded detailed-execution limit, initially justified by measurement (recommended starting point: 4 detailed executions, with additional active requests aggregated). Use one RAF only while an active visual transition exists, pause it in hidden tabs, and tear it down on completion, pagehide, and navigation.

## 12. Exact Event/Data Flow

1. A real client request reaches a Go data-plane handler.
2. The router chooses a backend target; Go emits request-correlated privacy-safe events already present in the current code.
3. The single `EventStreamClient` receives historical preload/live frames, records sequence cursor, and handles reconnect/gap policy.
4. `EventNormalizer` validates event shape, rejects malformed identity where correlation is impossible, maps known kinds, and ignores unknown kinds diagnostically.
5. `ExecutionTracker` groups events by existing privacy-safe `request_id`, applies sequence ordering, and updates only evidence-backed fields: request ID, public model/route when present, deployment, latency, attempt/failure/success signals, and terminal status.
6. `Activity` and `LiveTopology` subscribe to the same tracker snapshot.
7. `LiveTopology` maps known deployment IDs to authoritative snapshot provider/model metadata.
8. `VisualAgentRenderer` animates only a real live transition; reduced/off modes update static semantic state instead.
9. On terminal `route_ok`, supported terminal failure, client disconnect, or candidate exhaustion, the execution settles and the renderer returns to calm idle/history.
10. On SSE gap or restart evidence, fetch the authoritative snapshot and mark preloaded state historical; do not replay it as new motion.

Current limitation to preserve in the first mapping: no event should be interpreted as “attempt started” unless the backend provides that evidence. The first static slice may show gateway → actual failed/succeeded deployment transitions rather than inventing an unobserved start.

## 15. Performance Strategy

- No continuous RAF while idle.
- One bounded stream reader and one bounded retry policy.
- Keep the event history bounded at the existing frontend cap; use request-keyed bounded execution retention with terminal eviction.
- Batch burst event application before rendering.
- Update path/node classes and text regions rather than replacing the whole page each animation frame.
- Rebuild static topology only when snapshot configuration changes.
- Render at most a small measured number of detailed active executions; aggregate the rest.
- Pause or reduce expensive motion when `document.visibilityState !== 'visible'`.
- Abort stream and cancel RAF on pagehide/navigation.
- Measure idle CPU, active CPU, memory growth, DOM count, burst behavior, long-run retention, and hidden-tab behavior with browser evidence.

## 16. Accessibility Strategy

The visual agent itself may be `aria-hidden`. The same tracker state must be rendered in an accessible status/live region using real fields only, for example: request ID, public model, actual deployment, failure/failover, and measured completion latency. Provide keyboard-focusable request and node controls, visible focus, a non-motion static state, and a user-facing Live motion setting with On/Reduced/Off. `prefers-reduced-motion` must select Reduced behavior without relying on CSS alone.

Do not expose raw prompts/responses, API keys, authorization headers, or secret metadata in DOM, browser storage, logs, or event text.

## 17. Testing Strategy

Unit tests should cover normalization for every supported mapping, unknown/malformed events, request correlation, concurrent IDs, missing IDs, duplicate sequence, reordering, stale events, terminal cleanup, and bounded retention. Reconnect tests must cover cursor continuity and historical preload not animating.

Browser tests should retain all existing v0.14 provider, route, Connect, Activity, Settings, secret-safety, no-native-dialog, and reduced-motion coverage, then add deterministic local upstream cases for:

- one real request → real deployment → success;
- first upstream failure → backend-selected second upstream → success;
- all candidates exhausted;
- idle no-motion state;
- request selection/pinning;
- reduced/off static semantic state;
- pagehide cleanup;
- burst bound and background tab behavior.

Run `gofmt`, `git diff --check`, `go vet ./...`, `go test ./...`, race tests, `./scripts/verify.sh`, browser E2E, security checks, and available stress/build gates. Docker remains an environment gate already documented as unavailable in this sandbox.

## 18. Risks

- **Truthfulness risk:** current event vocabulary lacks consistent attempt-start evidence; visual semantics must be narrower or backend metadata must be added.
- **Reconnect risk:** current frontend does not preserve SSE cursor or detect gaps; duplicate/replayed animation is possible until the transport layer is refactored.
- **Restart risk:** event contracts/documentation claim epoch support that the current event struct does not expose.
- **Monolith risk:** adding renderer/state logic directly to the compact single-file app can make it unmaintainable; module compatibility must be proven first.
- **Performance risk:** unbounded per-request DOM/RAF would degrade the control plane under burst traffic.
- **Accessibility risk:** motion can become the only understandable signal unless an equivalent status/journey representation is built.
- **Privacy risk:** event messages and deployment metadata must remain bounded and must not acquire prompt/response/credential content.
- **Regression risk:** the current v0.14 flows are broad and must not be displaced by a heavier Overview.
- **Evidence risk:** concept art or mocked browser fixtures cannot satisfy the real visual acceptance gate.

## 20. Recommendation

Proceed safely, but **do not begin with animation**. First implement the shared event transport, normalization, and bounded request tracker, then evolve the existing Overview topology into a static real-execution surface. The current backend already supports a trustworthy initial correlation proof for `request_id`, deployment, failure/failover signals, and terminal success/failure. It does not yet support an unconditional “attempt started” semantic or documented epoch wire field.

Therefore the recommended initial acceptance target is: real request → real request-correlated event(s) → same request in Activity and Overview → actual deployment/result highlighted → calm idle, with no fabricated attempt state. After that proof, add only the smallest privacy-safe backend event/epoch delta if measured requirements demonstrate that the Visual Agent cannot otherwise represent a real journey. Do not merge PR #208, publish v0.14.0, or declare release completion; human visual review remains a required gate.
