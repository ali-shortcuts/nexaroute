# Verifying a NexaRoute release

Every GitHub Release ships the binaries, the installer bundle, a
software bill of materials (SBOM), a SHA-256 checksum manifest and a
Sigstore signature bundle for that manifest. Verify all three layers
before installing: the **signature** proves the manifest really came
from this repository's release workflow, the **checksums** prove
every downloaded file matches the signed manifest, and the **SBOM**
states exactly which components and Go module versions the binaries
contain.

Release assets:

| Asset | Purpose |
|---|---|
| `nexaroute-linux-amd64`, `nexaroute-linux-arm64` | gateway binaries |
| `nexaroute-videogen-linux-amd64`, `nexaroute-videogen-linux-arm64` | videogen binaries |
| `install.sh`, `video.example.json`, `VIDEO_GATEWAY.md`, `RELEASE_NOTES.md` | installer and documentation bundle |
| `nexaroute-<version>-sbom.spdx.json` | SBOM (SPDX 2.3 JSON, generated by Syft) |
| `SHA256SUMS` | SHA-256 manifest for payload assets above (excluding itself and its signature bundle) |
| `SHA256SUMS.cosign.bundle` | Sigstore bundle signing `SHA256SUMS` |

## 1. Verify the signature on the checksum manifest

Signing is *keyless*: the release workflow authenticates to Sigstore
with its GitHub Actions OIDC identity, so there is no long-lived
signing key to trust or leak. Verify with
[cosign](https://github.com/sigstore/cosign) (v3.x), pinning the
expected workflow identity and issuer — an unrestricted verify is not
a verification:

```sh
VERSION=v0.24.0   # current published stable release; use the exact tag you downloaded
cosign verify-blob \
  --bundle SHA256SUMS.cosign.bundle \
  --certificate-identity "https://github.com/ali-shortcuts/nexaroute/.github/workflows/release.yml@refs/tags/${VERSION}" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  SHA256SUMS
```

Expected output ends with `Verified OK`. A bundle produced by any
other workflow, repository or issuer fails this check, as does a
manifest modified after signing.

## 2. Verify every downloaded file against the manifest

```sh
sha256sum -c SHA256SUMS
```

Every listed payload file must report `OK`. The manifest covers all
distributable release payloads listed in the table: the four binaries,
the installer/configuration/documentation bundle, and the SBOM when
present. It excludes `SHA256SUMS` itself and
`SHA256SUMS.cosign.bundle`; the latter carries the Sigstore signature
over the manifest, rather than being a payload hashed by it.

## 3. Inspect the SBOM

The SBOM is SPDX 2.3 JSON generated by Syft from the shipped
binaries, so it reflects the Go module inventory actually embedded
in them (direct and transitive dependencies with exact versions),
the Go toolchain (`stdlib`) version, and the shipped files. Its
document namespace and comment record the source repository, the
release version and the exact source commit.

```sh
# Which version of a dependency shipped?
jq -r '.packages[] | select(.name == "go.etcd.io/bbolt") | .versionInfo' \
  nexaroute-${VERSION}-sbom.spdx.json

# Full dependency inventory:
jq -r '.packages[] | "\(.name) \(.versionInfo)"' \
  nexaroute-${VERSION}-sbom.spdx.json | sort -u
```

The release pipeline refuses to publish when the SBOM's module
inventory disagrees with `go.mod`, when any required asset is
missing, or when the manifest does not cover the asset set exactly.

## What gates a release

Before anything is published, the release workflow runs the full
repository verification, a `govulncheck` vulnerability gate over the
exact tagged revision (reachable vulnerabilities fail the release),
the installer lifecycle tests and the artifact checks above. The
non-publishing `workflow_dispatch` dry run exercises the same build,
SBOM, checksum and verification steps, plus a signing *mechanics*
test with a throwaway in-job key; that ephemeral bundle is never
uploaded and is **not** the release identity — only tag publishes
produce the keyless signature described in step 1.
